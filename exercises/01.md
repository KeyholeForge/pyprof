# Exercise 1: Setup and your first flame graph in Pyroscope

> Time: ~30 min

## Goal
You start the whole pyprof stack (Pyroscope, `origin`, the `pixelforge`
application), connect the application to continuous profiling and see your
first CPU flame graph in the Pyroscope UI — before you diagnose anything, you
need a working "measuring instrument".

## Theory in a nutshell
- **Continuous profiling** — regular sampling of a process's call stack (for
  example 100 times/s), aggregated over time and sent to a backend. Unlike a
  one-off profile, it lets you look back and compare time periods.
  (→ `00-theory.md`, `glossary.md`)
- **Flame graph** — a visualization of a profile: the width of a frame = the
  share of the samples in the selected time window in which that function
  appears at this point in the stack, including the functions it calls; the
  vertical position = stack depth. A wide frame = a lot of sampled cost along
  that stack path, not "long-running" and not "called many times".
- **What this CPU profile counts** — in the course's CPU mode (`oncpu=True,
  gil_only=True`) a sample is taken only from a thread that holds the GIL and
  is not idle. CPU work done while the GIL is released — for example parts of
  Pillow's resizing, JPEG decoding and blur — is not counted during those
  intervals, so frame width is a share of these GIL-holding CPU samples, not
  of the whole CPU time of the process (more in exercise 11).
- **Sample rate** — how often the stack is sampled (Hz). Higher = more chances
  to catch short stacks and, under a comparable workload, less statistical
  noise, but more overhead on the profiled application.
- **`pyroscope.configure()`** — one-time initialization of the Python SDK
  client. The course calls it in `lifespan` (`app/main.py`), before the
  application starts handling requests, so the profile covers the traffic from
  the very start. Calling it again while the agent is already running is
  **refused**: it returns `False` and leaves the mode and tags unchanged
  (`pyroscope-io` 1.4.0) — that is why you choose the profiler mode (CPU or
  wall-clock, exercise 11) at process start, and changing it means a restart.
- **Samples exist only since the profiler started** — it does not backfill the
  past. After every application restart, generate traffic first, then look for
  it in the UI. Data shows up with a delay (in my runs about 15–20 s — an
  observation, not a guarantee).

## Steps
1. Environment (Python 3.11–3.14, standard build with the GIL):
   `python3.14 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`.
   On macOS, `python3` may be the system 3.9 from the Command Line Tools (and
   plain `python` may not exist at all) — use `python3.14` (or another 3.11+
   version). Note: `uv venv --python 3.14` may pick a free-threaded build
   (3.14t), on which `pyroscope-io` does not install (in my run: "does not
   support free-threaded CPython"); with uv, ask for the GIL build explicitly:
   `uv venv --python 3.14+gil`. Check the build in the activated environment:
   `python -c "import sysconfig; print(sysconfig.get_config_var('Py_GIL_DISABLED'))"`
   → `0` or `None` (3.11 and 3.12 do not define this variable); `1` means a
   free-threaded build.
2. Data corpus: `python scripts/gen_corpus.py` (it must exist BEFORE `origin`
   starts — `origin` mounts `data/origin_images` as a volume).
3. Backend: `docker compose up -d --build --wait` — the first run builds the
   images (Pyroscope 2.4.2, `origin` = nginx 1.30), so it takes a few minutes;
   `--wait` waits until the containers are healthy (after startup Pyroscope
   returns 503 on `/ready` for a while — in my runs up to about 90 s; the
   health check allows for that).
   Check: `curl -f http://127.0.0.1:4040/ready` and `curl -f http://127.0.0.1:8041/`.
   The ports are exposed only on `127.0.0.1`.
4. `cp .env.example .env` (the course has no secrets — only local addresses).
   The application does not load this file itself: the defaults in
   `app/config.py` are the same, and you override a value by exporting the
   variable before you start uvicorn.
5. In **`app/profiling.py`**, implement `init_profiling()` — add
   `import pyroscope` at the top of the file and call
   `pyroscope.configure(application_name=app_name, server_address=server_address,
   sample_rate=100, oncpu=True, gil_only=True, tags=tags or {})`, then
   save the parameters in `_STATE` and set `_STATE["configured"] = True`
   (the exact description is in the function's docstring). The signature also
   has a `wall` parameter — for now you ignore it (you will handle wall mode in
   exercise 11).
6. Start the application: `uvicorn app.main:app --host 127.0.0.1 --port 8040`.
   In the uvicorn terminal you should see
   `INFO:     pixelforge: Profiling active (Pyroscope: http://127.0.0.1:4040, mode: cpu)`
   instead of the `Profiling inactive` warning. A second way to check —
   from a second terminal: `curl -s 127.0.0.1:8040/health` → in the `profiling`
   field `"configured": true` (and `pid` gives you the process PID, which you
   will need in exercises 2 and 8). In this exercise both signals only show
   that the application ran its setup and set its local flag — the code does
   not check the value `configure()` returns. Neither proves that the SDK
   started successfully or that samples arrived. Inspect the profile in a time
   window covering only your run in step 9. `python check.py ex01` checks for
   profile data for the service in its time window, not which process sent it.
7. Generate traffic: `python loadgen.py --duration 20 --concurrency 3`
   (short form: `-c 3`). At startup loadgen uploads a pool of 100 images and
   only then measures traffic; the pool uploads are excluded from the loadgen
   summary but may appear in the profile. In the default `mixed` scenario each
   iteration chooses a scenario with equal probability; the counts vary across
   runs, and the summary counts scenarios, not endpoints.
8. **Before you open the UI:** which endpoint handler — a function in
   `app/main.py`, for example `get_thumbnail` or `fetch_image` — do you expect
   to contribute the most recorded samples? Think about how often it runs and
   how much of its work this profiler can sample. Write your guess down.
   (Handlers are not in the top row: above them sit the root `total` and the
   thread and framework frames — look a few levels down, or use the search
   field.)
9. Open `http://127.0.0.1:4040`, select the service `pixelforge` and the
   profile type `process_cpu` (the name is misleading: the wall-clock profile
   from exercise 11 lands under the same type too — there you add a `mode` tag
   that tells them apart), and look at the flame graph for a time window that
   covers only this run. Compare the visible handler frames in that window
   with your hypothesis from step 8; pick a wide one and read its callers and
   the functions it calls. A handler frame shows that function's share at
   this point in the stack, not the whole CPU cost of its route: the framework
   does part of the route's work outside the handler, and small branches may
   be merged into `other`. If your predicted handler is missing, that is not
   evidence it did no work.
   If the UI is empty and the log says "active": check the time range, the
   selected service and profile type, that the traffic went to the current run
   of the application (not to the previous one, before the restart) and that
   loadgen reported no errors — then wait 20 s and refresh. If it is still
   empty, repeat the `/ready` check from step 3 and look for errors in the
   uvicorn terminal.

## Definition of done
- [ ] `docker compose ps` shows `pyroscope` and `origin` as `healthy`
- [ ] `uvicorn app.main:app --host 127.0.0.1 --port 8040` starts without the
      `Profiling inactive` warning, and `curl -s 127.0.0.1:8040/health` shows
      `"configured": true`
- [ ] In the Pyroscope UI (`http://127.0.0.1:4040`) you see the service
      `pixelforge` with a non-empty flame graph
- [ ] `python check.py ex01` prints `[PASS] ex01`. It requires `/health` to
      report `"configured": true` **and** Pyroscope to have a nonzero
      `pixelforge` profile in the window since the application started, capped
      at the last hour; it does not check the PID or the profiler mode. On
      `FAIL`, read the reason; if it says there are no samples, generate fresh
      traffic and allow 15–20 s for the upload. `[SKIP]` means the application
      or Pyroscope did not respond.
- [ ] You understand the difference between a "wide frame" and a "long-running
      function"

## Review questions
1. What exactly does the width of a frame on a CPU flame graph mean — the
   duration of the function or its share of the samples?
2. Why does the course call `init_profiling()` at startup (in `lifespan`),
   before the first request is handled, rather than lazily on first use?
3. What happens to the profile if you set `sample_rate` very low (for example
   1 Hz) on an application that handles a request in 5 ms?

## ★ Bonus (optional)
Change `sample_rate` in `init_profiling()` to 20 and restart the application
(`configure()` in a running process changes nothing). Generate the same traffic
again and compare two separate, equally long windows — one entirely within the
100 Hz run, one entirely within the 20 Hz run, covering similar phases of the
traffic. Do you see a difference in the "graininess" of the narrow frames?
The `mixed` traffic is random, so a single difference in shape does not by
itself prove the effect of the sample rate.
