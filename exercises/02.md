# Exercise 2: py-spy — inspecting a live process without a restart

> Time: ~20 min

## Goal
You look at the call stack of the RUNNING pixelforge process from the outside,
without restarting it or adding code — exactly what you do in production when a
process "hangs" or eats CPU and you cannot restart it in the middle of a
diagnosis.

## Theory in a nutshell
- **py-spy** — a Python stack sampler that works from OUTSIDE the process (it
  reads the process's memory through the operating system), so it needs no
  change to the application code and no restart. It is not free, though: by
  default py-spy pauses the process for a moment while it reads each sample
  (`--nonblocking` avoids the pause at the cost of possibly inconsistent
  samples); the service keeps running. (→ `glossary.md`)
- **`py-spy top`** — a "live" mode, similar to the operating system's `top`,
  that ranks **functions** by how often they appear in the samples. By default
  it sorts by `OwnTime` — the sampled time accumulated since you started `top`
  while the function itself was at the top of the stack. `OwnTime` and
  `TotalTime` are sample counts multiplied by the sampling interval, not
  measured call durations. The `%Own` and `%Total` columns describe only the
  last refresh: how often the function was at the top of the stack or anywhere
  on it in those samples — not measured CPU, and they need not add up to 100%.
  By default `top` skips idle threads (`--idle` includes them).
- **`py-spy dump`** — a one-off snapshot of the stack of every Python thread at
  a given moment — good for catching "what is happening right now". One
  snapshot is one sample: it can miss a function that runs most of the time.
- **Permissions.** py-spy reads the memory of another process, which the
  operating system allows only to privileged users:
  - **macOS:** always `sudo` — macOS lets only root (or a signed debugger) read
    another process's memory. System Integrity Protection (SIP) is a separate,
    additional block: even root cannot read SIP-protected binaries such as
    `/usr/bin/python3`, so run the application on a Python from `uv`,
    python.org or Homebrew.
  - **Linux:** attaching to a running process by PID usually needs `sudo` too.
    Without it, it works only if the system's policy and your permissions
    allow it (for example `kernel.yama.ptrace_scope` = 0 for a process of your
    own user, or `CAP_SYS_PTRACE`) — do not change that policy just for this
    exercise.
  - `sudo` may not find the `py-spy` installed in your virtual environment;
    then run `sudo "$(command -v py-spy)" …` or `sudo env "PATH=$PATH" py-spy …`.
  - **In a Linux container** started with `--cap-add SYS_PTRACE` (as in
    exercise 10), py-spy works without `sudo` on processes of the same
    container. With Docker's default PID isolation it does not see the host's
    processes, so for a pixelforge running on the host the rules above apply.
    If you cannot use `sudo`, do the **whole exercise in one container**,
    started with `--cap-add SYS_PTRACE` and an interactive terminal (`-it`;
    `top` needs it):
    - the container needs a copy of the course repository (for example
      mounted with `-v "$PWD:/w" -w /w`); install `requirements.txt` there and,
      if `data/corpus/` is missing, run `python scripts/gen_corpus.py` (README,
      Quick start) — without the corpus loadgen stops before sending any
      traffic;
    - open the second and third terminal in the **same** container with
      `docker exec -it <container> bash` (another `docker run` would start a
      separate container that does not see this application);
    - the `slim` image has neither `curl` nor `ps`: install curl
      (`apt-get update && apt-get install -y curl`) or read the PID in step 2
      with Python:
      `PID=$(python -c "import json, urllib.request; print(json.load(urllib.request.urlopen('http://127.0.0.1:8040/health'))['pid'])")`;
    - run steps 1–7 (and the bonus, if you do it) and `python check.py ex02`
      inside it, without `sudo`; with a mounted repository the files in
      `profiles/` stay on your disk after the container is removed.

    Practising the commands on `solutions/gil_demo.py` (exercise 10) teaches
    the tool, but it does not complete this exercise: `check.py ex02` needs a
    pixelforge dump.

## Steps
1. Start the application: `uvicorn app.main:app --host 127.0.0.1 --port 8040` (in one terminal).
2. In a second terminal, find the PID of the uvicorn process:
   `curl -s 127.0.0.1:8040/health` — the `pid` field (no guessing with
   `pgrep`). Save it in this terminal; you will run py-spy here:
   `PID=$(curl -s 127.0.0.1:8040/health | python -c "import sys, json; print(json.load(sys.stdin)['pid'])")`.
3. **Before you generate traffic:** the next step sends requests for three
   filters, `grayscale`, `blur` and `sepia`, drawn at random with equal odds.
   Which filter's code do you expect to dominate the `py-spy top` ranking? Why?
   (A hint on scale, from the author's single run on one machine — your numbers
   will differ: on the largest image in the corpus, 1.5 MB, a single request
   took about 18 ms for `grayscale`, 47 ms for `blur` and 730 ms for `sepia`.)
   Remember that `top` ranks functions, not filter names: sepia is a pure
   Python loop, `_sepia_naive` in `app/images.py`, while `grayscale` and `blur`
   run inside Pillow functions (e.g. `grayscale`/`convert`, `filter`) called
   from `apply_filter`. `convert` and the JPEG `save` run for every filter, so
   in `top` press `L` to see line numbers and tell the branches of
   `apply_filter` apart.
4. In a third terminal, generate continuous traffic:
   `python loadgen.py --duration 180 --concurrency 5 --scenario filters`.
   loadgen first uploads its pool of images and only then starts counting the
   180 s (it prints a line when the pool is uploaded). `--concurrency 5` means
   five clients sending requests at the same time. Start steps 5 and 6 after
   that line appears, while loadgen is still running — if it has finished,
   start it again.
5. Live top: `sudo py-spy top --pid $PID`. Watch for about 15–20 s under the
   load from step 4. `top` is interactive and needs a real terminal (TTY), so
   run it directly in a terminal window, not in a pipe.
6. Snapshot with local variables, still under load:
   `sudo py-spy dump --pid $PID --locals > profiles/ex02_dump.txt`.
   Open the file. Each thread starts with a header `Thread <id> (<status>)`;
   py-spy adds a thread name only when it can read one, and in this
   application it usually cannot. You will see the frames of the pool's worker
   threads (the `anyio` `WorkerThread`s, which is where the `def` endpoints
   run; `run (anyio/_backends/_asyncio.py)` sits just above the `threading.py`
   start-up frames at the bottom of their stacks) and of the main event loop
   thread (between events it usually waits in `select`). Find the
   `_sepia_naive` frame (if one of the threads happened to be in it at the
   moment of the dump — it is a single snapshot, you may need to repeat it)
   and check whether you can see the local variables (`x`, `y`, `r`, `g`, `b`;
   a variable not assigned yet is missing).
   Look at the status in the thread headers: in this CPython with the GIL only
   one thread at a time can be `active+gil`; another thread in `_sepia_naive`
   may show `idle` — one possible reason is waiting for the GIL (more in
   exercise 10) — and `py-spy top` skips idle threads by default.
   `--locals` and the command line in the dump header can contain sensitive
   data — use them on your own application with test data, as here.
7. Compare the result with your hypothesis from step 3.

## Definition of done
- [ ] `py-spy top --pid <PID>` shows live data without crashing the process
- [ ] `profiles/ex02_dump.txt` contains a dump of the pixelforge threads taken
      under load: its `Process <pid>` line matches the `pid` from `/health`,
      and the stacks contain `app/...` frames
- [ ] `python check.py ex02` passes — a content heuristic: the file must not be
      empty or a template and must contain the text `Thread` and `app/`.
      It does not check the PID, `--locals`, the load or `top`; a dump taken
      after the traffic ended usually has no `app/` frames and fails
- [ ] You understand why py-spy does NOT require any change to the application code

## Review questions
1. How do `py-spy top` and `py-spy dump` differ in WHAT you observe and for HOW
   long?
2. Why does `py-spy` need `sudo` on macOS, while inspecting your own process
   (for example with `tracemalloc`) does not?
3. A single `py-spy dump --locals` taken during the `filters` scenario showed
   3 of the 5 busy worker threads of the pool in `_sepia_naive`. What does this
   tell you about sepia requests compared with the other filters — and what
   does it NOT tell you?
