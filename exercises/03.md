# Exercise 3: cProfile + snakeviz — an offline profile of a single function

> Time: ~25 min

## Goal
You profile a single function OFFLINE (no HTTP server, no Pyroscope) and look
at the result in snakeviz — a technique that is useful when you want to examine
exactly ONE piece of code, without the noise of the whole application around it.

## Theory in a nutshell
- **`cProfile`** — Python's built-in deterministic (tracing) profiler (not a
  sampling one like py-spy/Pyroscope). Instead of periodically looking at the
  stack, it records supported call events: here, the calls and returns of
  Python functions and of selected built-ins such as `min`. The call counts are
  exact for the events it records, but the instrumentation adds overhead
  (usually more than a sampling profiler) and can distort the timings and
  their proportions. (→ `glossary.md`)
- **`.prof`** — the binary output format of cProfile (`pstats`), readable by
  tools such as `snakeviz` or `pstats.Stats`. Read it with the same Python
  version that wrote it.
- **snakeviz** — shows a `.prof` file as an interactive "icicle"/sunburst chart
  in the browser; it starts a local HTTP server and does not modify the file.
  The `tottime` column (time spent IN THIS function, excluding the functions it
  calls) and the `cumtime` column (time spent IN THIS function + all the
  functions it calls) are different numbers.
- **Sampling profiler (py-spy/Pyroscope) vs deterministic profiler (cProfile)**
  — a sampling profiler usually has much lower overhead (but not zero) and
  suits long runs and production, but it can miss very short calls; a
  deterministic one gives exact call counts for the calls it records in a
  single, short offline run, at the cost of overhead that can distort the
  timings.

## Steps
1. Work from the repo root, in the course environment with the dependencies
   from `requirements.txt` installed. Make sure the corpus exists:
   `python scripts/gen_corpus.py` (if you have not run it in this repo yet).
2. **Hypothesis first:** open `_sepia_naive` in `app/images.py` and, before you
   run anything, predict: which function will have the highest `tottime` (not
   `cumtime`) — `_sepia_naive` itself, or a function it calls? And how many
   times will `min` be called for one large image of 2000×1500 = 3,000,000
   pixels?
3. Run the ready-made reference script: `python solutions/profile_sepia.py`
   — it profiles `_sepia_naive` from `app/images.py` on one large image from
   `data/corpus/`, saves the result to `profiles/ex03_sepia.prof` and prints
   the top 15 functions by `cumtime` to stdout. In my run: 9,000,027 function
   calls and about 1.5 s (the time depends on the machine, the exact count on
   the Python and Pillow versions). The stdout list is sorted by `cumtime`, so
   check your hypothesis on the full profile sorted by own time:
   `python -m pstats profiles/ex03_sepia.prof`, then at its prompt type
   `sort tottime`, `stats 5` and `quit`. Why are there exactly 9,000,000 `min`
   calls, and where does the small rest of the total come from?
4. Look at it visually: `snakeviz profiles/ex03_sepia.prof` (it tries to open
   the browser; if it cannot, run `snakeviz -s profiles/ex03_sepia.prof` and
   open the address it prints). The chart shows where the measured time goes
   along the call tree; frame sizes are based on the time attributed to each
   branch, not a direct readout of the `cumtime` column. Read the exact
   `tottime` and `cumtime` values in the table below the chart. How
   much of the total time falls on `_sepia_naive` alone (`tottime`, in my run
   1.2 s) vs on `min` (9,000,000 calls, about 0.35 s)? Note what cProfile does
   NOT show as separate rows: in this run the indexing `src_pixels[x, y]`, the
   `int(...)` conversion and the arithmetic get no rows of their own, so their
   cost lands in the `tottime` of `_sepia_naive` itself.
5. Compare with your hypothesis from step 2. For perspective: in my run the
   same image under the `timeit` command from exercise 6 took about 0.7 s per
   call without cProfile. That is a different kind of measurement (the best of
   several repeats, with the garbage collector off), so treat it only as a
   rough comparison: in these runs the profiled time was about twice the
   `timeit` result. This shows how different the reported times can be; it
   does not isolate the profiler's overhead or the cost of recording `min`.
   **Absolute values from cProfile are not the time "in production"**, and
   with millions of tiny calls even the proportions can be skewed — in my run
   the `tottime` of `_sepia_naive` alone (1.2 s) was longer than the whole run
   without the profiler. Use cProfile as a map of where the calls go and which
   function to look at; use `timeit` to benchmark this isolated call and a
   sampling profiler to cross-check hotspots under load.
