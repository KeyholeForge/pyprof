# Exercise 5: Diagnosing and fixing a naive CPU filter (F2)

> Time: ~30 min

> First read the reading `04a-cpu-internals.md` — it builds a concept map for
> the CPU block (exercises 5–6) before you start diagnosing.

## Goal
You use a profile (not by reading the code up front) to diagnose why the
`sepia` filter is much slower than `grayscale`/`blur`, and you fix it by
replacing the hand-written Python loop with a vectorized Pillow operation.

Before you start, exercises 1 and 4 must be done: the image corpus is
generated, `pyroscope` and `origin` are running
(`docker compose up -d --build --wait`), `init_profiling` works and
`app/profiling.py` has a working `tag_wrapper` and the exercise 4 CPU settings
(`oncpu=True`, `gil_only=True`) — or copy the reference version:
`cp solutions/ex04_profiling.py app/profiling.py`. Without `tag_wrapper` the
profile has no `endpoint`/`filter` tags.

## Theory in a nutshell
- **A pure-Python loop over pixels** — for a 2000×1500 image that is
  3,000,000 interpreter iterations; each one carries bytecode overhead that a
  native (C) operation in Pillow does not have. (→ `glossary.md` — "vectorization")
- **`Image.load()` + `[x, y]` indexing** — gives pixel-by-pixel access from
  Python code: every access goes through Pillow's pixel-access object
  (building a coordinate tuple and a pixel tuple each time), and a profiler
  attributes this work to the loop's own frame.
- **Linear channel transform** — sepia is a 3×3 matrix multiplication
  (+ an offset) on the RGB vector; Pillow has `Image.convert("RGB",
  matrix=...)` for this, which runs the per-pixel loop in native code. Both
  versions stay linear in the number of pixels (O(n)); what changes is where
  the loop runs.
- **CPU-bound vs I/O-bound** — the naive transform is purely computational
  (CPU), so the CPU profile (`oncpu=True`) shows it as a wide frame of Python
  code — unlike the network/disk flaws from Block E. The profile shows sampled
  CPU weight; it does not measure how long a request waits.

## Steps
1. Start the application (`uvicorn app.main:app --host 127.0.0.1 --port 8040`)
   and generate traffic focused on filters (each request picks one of the
   three filters at random with equal odds, so about a third are sepia):
   `python loadgen.py --duration 30 --concurrency 5 --scenario filters`.
   Write down when the run starts and ends and what loadgen prints: requests,
   errors and p50/p95 — this is your "before". (The summary counts failed
   requests too, its percentiles include their times, and it includes
   requests that started before the 30 s deadline and finished after it.)
2. **Before you look at the profile:** by how many times (order of magnitude) do
   you expect `sepia` to be slower than `grayscale` on a large image (2000×1500)?
3. Check the hypothesis with timings, without other traffic. First wait until
   Pyroscope shows the step 1 traffic up to its end (the SDK sends profiles in
   batches of roughly 10 seconds, see exercise 4): the requests below carry
   the same tags, and they must not fall into the range you analyze in
   step 4. Then upload one large image and time single requests for each
   filter on it (the first large image, the same one
   `solutions/profile_sepia.py` and exercise 6 use):
   ```bash
   IMG=$(ls data/corpus/*_large_*.jpg | head -1)
   ID=$(curl -fsS -F "file=@$IMG" 127.0.0.1:8040/images | python -c "import sys, json; print(json.load(sys.stdin)['id'])")
   echo "ID=$ID"
   for f in grayscale blur sepia; do for i in 1 2 3 4 5; do
     curl -sS -o /dev/null -w "$f %{http_code} %{time_total}\n" 127.0.0.1:8040/images/$ID/filter/$f || printf '%s\n' 'TRANSFER FAILED'
   done; done
   ```
   Each timing line shows the filter, the HTTP status and the time in
   seconds. Use the block only if it printed a non-empty `ID`, all 15 timing
   lines show `200`, and no `TRANSFER FAILED` line appeared (a response can
   start with `200` and still break off before the end). Otherwise fix the
   cause (for example a missing corpus) and rerun the whole block. Take the
   median of the five times for each filter. `time_total` is the client-side
   time of the whole request: it includes decoding, JPEG encoding and writing
   the result file, not only the filter. (Historical single-request example
   from the author's machine, not five-request medians — your numbers will
   differ: about 18 ms for
   `grayscale`, 47 ms for `blur` and 730 ms for `sepia` per request.)
4. In Pyroscope, take ONE time range that covers only the step 1 traffic
   (leave out a batch that overlaps the step 3 requests) and select
   `endpoint=filter`; sort the table by Self to identify the function with the
   largest own contribution (`_sepia_naive`). Then compare `filter=sepia`,
   `filter=grayscale` and `filter=blur` by the absolute Total of the root
   (tooltip of the root frame) in that same range, not by the width of their
   frames: every filtered flame graph is scaled to its own 100%. The profile
   shows *where* the CPU goes, not how many times slower a filter is: with
   `gil_only=True` only threads holding the GIL are sampled, and Pillow
   releases the GIL during parts of its native work (JPEG decoding, `convert`,
   `GaussianBlur`).
5. Confirm offline: `python solutions/profile_sepia.py` (from exercise 3).
   Expect the `cumtime` of `_sepia_naive` to cover nearly all of the recorded
   run, most of it as its own `tottime`, plus `builtins.min` with exactly 3
   calls per pixel. Do not read `min`'s time as the culprit: cProfile inflates
   the cost of millions of tiny calls, and the fix is to remove the loop, not
   `min`. Do not use these times to compare Python with C either: for the
   end-to-end effect, use step 3; to compare the two implementations in
   isolation, use exercise 6.
6. Fix it: in **`app/images.py`** add a `SEPIA_MATRIX` constant (a 3×3 matrix,
   see `solutions/filters_snippets.py`) and in `apply_filter` replace the
   `sepia` branch from `_sepia_naive(img)` with `img.convert("RGB", matrix=SEPIA_MATRIX)`.
   Keep the `_sepia_naive` function defined: `solutions/profile_sepia.py` and
   exercise 6 import it. Remove only its call.
7. Restart the application (the profile and code changes only take effect
   after a restart) and repeat steps 1, 3 and 4 with the same parameters, on
   fresh data: a new time range, kept separate from the step 3 requests in
   the same way, and a new upload. Write down and compare:
   - the step 3 medians before and after (in the author's historical
     single-request example, sepia went from 730 to about 15 ms per request,
     about ×49). The expected result is a lower sepia median after the
     change. If a valid comparison does not show it, check that you
     restarted the application after the change, that `apply_filter` uses
     the matrix in the sepia branch and that the timing conditions match.
     Report the observed medians without claiming a speedup if they do not
     support it;
   - loadgen's requests, errors and p95. The same parameters mean the same
     configuration, not the same traffic: in this closed loop the two runs can
     complete different numbers and mixes of requests, so these numbers do not
     isolate the cost of the filter. Every successful filter request still
     encodes and writes its result file (the disk flaw F4 from exercise 14),
     so the change also depends on your disk and OS;
   - the root Totals of the filter tags within the after-fix range. Do not
     compare the before and after Totals directly: two runs of the same
     length can carry different numbers of requests.

   In the after-fix range, check whether `_sepia_naive` still shows up and
   which function now has the largest Self. The fix removes the call from the
   sepia branch; the matrix conversion runs in C and releases the GIL while
   it processes each row, so this CPU profile sees only part of it (its
   `Image.convert` row also counts the other conversions in `apply_filter`).
   Whatever function has the largest
   Self now tells you what is left of the GIL-holding work, not which step of
   the request is the most expensive.

## Definition of done
- [ ] `python check.py ex05` passes — a static check: it only looks for the
      text `matrix=SEPIA_MATRIX` in `app/images.py`; the criteria below check
      the result
- [ ] You have the "before" and "after" numbers written down: the step 3
      medians from complete, valid step 3 blocks on the same image (if the
      sepia median is not lower after the fix, you checked the causes listed
      in step 7), loadgen's requests, errors and p95 with the same
      parameters, and the root Totals of the filter tags in each range
- [ ] In the after-fix range you noted whether `_sepia_naive` still shows up
      in `endpoint=filter` and which function has the largest Self (no
      particular ranking is required)
- [ ] `GET /images/$ID/filter/sepia` (the `ID` printed in step 3 after the
      fix) returns `200` and a valid JPEG (the image looks sepia-toned, not
      corrupted)
- [ ] You understand why the visual result is practically the same despite a
      completely different implementation (the same coefficients; in RGB,
      before JPEG encoding, a channel value may differ by 1 level because
      Pillow rounds while the loop truncates)

## Review questions
1. Why is the Pillow matrix operation faster, even though it uses the same
   coefficients as the loop?
2. What would happen to the execution time of `_sepia_naive` if you shrank the
   image to 200×200 before filtering? Would that fix the CAUSE, or only reduce
   the SYMPTOM?
3. What would the profile look like if the flaw were reversed — `grayscale`
   slow and `sepia` fast? What would that suggest about the cause?
