# Exercise 4: Reading flame graphs + per-endpoint tagging

> Time: ~35 min

## Goal
You add per-endpoint tags to the profile (`tag_wrapper`), so in Pyroscope you
can filter the flame graph down to ONE endpoint instead of looking at a blend
of all the traffic. You finish the "Foundations" block with a mini-incident:
you diagnose a flaw ONLY through the UI.

Before you start, exercise 1 must be done: the image corpus is generated,
`pyroscope` and `origin` are running (`docker compose up -d --build --wait`),
and `init_profiling` works.

## Theory in a nutshell
- **Tag (label)** — metadata attached to profile samples (for example
  `endpoint=thumbnail`): either to all of them (global tags in
  `pyroscope.configure`) or, with `tag_wrapper`, to the samples taken on one
  thread while a block of code runs. Pyroscope lets you filter the profile by
  tags — like `WHERE` in a query. (→ `glossary.md`)
- **`pyroscope.tag_wrapper(tags: dict)`** — a context manager from pyroscope-io
  (1.4.0 in our case): samples collected INSIDE the `with` block get the given
  tags. Mind the scope: the tag is set **per thread**, not per request, and it
  does not follow work handed over to another thread.
  For `def` endpoints (thumbnails, filters, reports) a synchronous handler runs
  on a worker thread from the pool for as long as it executes, so this works
  reliably. For `async def` (upload, fetch, fetch-batch), all coroutines share
  one event loop thread, so the tags of concurrent requests get mixed — we will
  come back to this in exercise 11.
- **Flame graph shapes** — "plateau" (one wide frame with a large self share —
  often a pure-Python loop or one long call into C code), "comb" (many narrow
  frames side by side under a common parent — the cost is spread over many
  different call paths), "tower" (a deep stack — a long chain of calls or
  recursion). These are reading heuristics: a shape points to a candidate to
  investigate, not proof of a flaw. A wide frame is not a flaw by itself either.
- **Diagnosis without reading the code** — a skill this course trains: being
  able to point at the SUSPECT module/function looking ONLY at the shape and
  width of the frames, before you open the editor.

## Steps
1. In **`app/profiling.py`**, implement `tag_wrapper()` — it delegates to
   `pyroscope.tag_wrapper(tags)` (see the function's docstring; you call it the
   same way as the library's function).
2. Stop the application if it is still running and start it again:
   `uvicorn app.main:app --host 127.0.0.1 --port 8040`. `app/main.py` already
   wraps the request handlers (all except `/health` and the debug endpoints)
   with the `_instrumented(tags)` helper, so after this change they
   automatically start being tagged (`endpoint=...`, for filters also
   `filter=...`, for thumbnails `size=...`).
3. Generate varied traffic (after the restart — the profiler collects samples
   only since the start): `python loadgen.py --duration 30 --concurrency 5 --scenario mixed`.
   Wait about 15–20 s before you look for the tags in the UI.
4. **Before you open the UI:** which `endpoint` tag (out of `upload`,
   `thumbnail`, `filter`, `fetch`, `fetch-batch`, `reports-batch`) do you
   expect to have the largest share of the CPU samples? For every request,
   loadgen picks one of five scenarios, each equally likely, and `fetch` and
   `fetch-batch` split the fetch scenario about half and half. So `upload`,
   `thumbnail`, `filter` and `reports-batch` get a roughly similar number of
   requests, and `fetch` and `fetch-batch` about half of that each. Why that
   one in particular?
5. In the Pyroscope UI, select the `pixelforge` service and keep ONE fixed time
   range for all the comparisons below. Note when the mixed traffic starts
   (after loadgen prints that its pool of images is uploaded — those 100
   uploads are tagged `endpoint=upload` too) and when the workers finish. The
   SDK sends profiles in batches of roughly 10 seconds, so these times are only
   approximate cutoffs: leave out a starting batch that still overlaps the pool
   uploads, even if that drops some mixed traffic, wait for the last batch to
   arrive, and note the time range you actually compared.
   - Select each `endpoint=...` value in turn and note the total CPU of the
     selection (the root frame's tooltip). The largest total ranks the
     compared selections and answers step 4 — it says nothing about single
     requests or about all the CPU of the service. Keep in mind that the
     totals of the `async def` endpoints (`upload`, `fetch`, `fetch-batch`)
     are only approximate (see the theory).
   - Open `endpoint=filter` and check which function has the most **self**
     samples: sort the table by Self. The tooltip describes one frame at one
     position in the stack; the table groups the results by function.
   - Compare `filter=sepia` with `filter=grayscale` by their totals in the same
     time range, not by the width of their frames: every filtered flame graph
     is scaled to its own 100%, so widths from two separate views cannot be
     compared. A larger total means more CPU in that window, not yet a higher
     cost per request (that also depends on how many requests of each kind
     ran).

   Confirm or reject your hypothesis from step 4.
   (The order of magnitude in my run: in the `endpoint=filter` profile, the
   `_sepia_naive` function had 86–98% of the self samples — the other filters
   disappear next to it. Your numbers will differ.)
6. **Mini-incident (10 min):** Someone reports that `POST /images` (upload) is
   "strangely slow" under load, even though saving the file itself looks
   simple. Generate traffic focused on upload: `python loadgen.py --duration 30
   --concurrency 8 --scenario upload` (this scenario sends only uploads and
   uploads no pool). In Pyroscope, look at the whole `pixelforge` profile for
   that time range first, then filter to `endpoint=upload`. Upload is an
   `async def` endpoint, so this filter is only approximate: it selects the
   samples carrying `endpoint=upload`, not a complete profile of an upload
   request, and with overlapping uploads it can both include work that is not
   the upload handler's and miss part of it. FastAPI parses the multipart
   request body BEFORE your handler (and its `with` block) starts, so any
   parsing frames under this tag are not that handler's own work: they can get
   the tag, for example, when the event loop parses another request while an
   upload waits inside its block for a file over 1 MiB to be read in a worker
   thread. Do not read their share under this tag as the parser's cost per
   upload. **WITHOUT
   opening `app/storage.py`**, write down your hypothesis: based on the flame
   graphs alone, where does the **CPU** cost of the upload path lie (parsing
   the request? image processing? the file-saving code?), and what can this
   CPU profile **not** tell you about the reported slowness? Only then look
   into `app/storage.py` and check whether you were right (this is a preview
   of exercise 14 — F4). What to expect is at the end of the exercise 4
   section in `solutions/review_questions_answers.md` — read it only after you
   have written down your hypothesis.

## ★ Bonus (optional)
Add your own extra tag in `_instrumented` for the `thumbnail` endpoint — for
example `{"size_bucket": "small" if size <= 64 else "large"}` — and check in
Pyroscope whether the `large` bucket takes more CPU in total than `small` over
the same time range. Compare totals, not frame widths from two views. A larger
total can also come from more requests or fewer thumbnail cache hits
(`images.get_thumbnail` caches by `(id, size)`), so it is not yet the cost of a
single thumbnail. The bucket tag has only two values, while `size` has
hundreds, and every distinct set of tags is a separate series in Pyroscope. To
reduce the number of thumbnail series, replace the `size` tag with
`size_bucket`; adding it while keeping `size` does not reduce the number of
distinct tag sets.
